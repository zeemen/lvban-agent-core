# 知识库交接清单 · 数据组 → 产品

2026-11-27 定。数据组在另一台机器上完成了部分知识库建设，这份清单是把它接进产品
要走的事。**交接契约见 [`supply-chain-contract.md`](supply-chain-contract.md)，这份只是那份的执行面。**

**第零件事：产品连不上你们那台机器。** 产品认的接入面只有三样——
`WEKNORA_BASE_URL`、`WEKNORA_KB_IDS`、一个 capability 只给 `retrieve` 的 API key
（`src/knowledge/weknora.ts:140`）。知识库活在你们机器的 Docker 卷里，我们这边配什么都
指不过去。所以第一步不是「配一下」，是**把库并到共用实例**。

## 一、先分清产出的是哪一类物料

契约第一节定了两条路，不是一条：

| 物料 | 交付方式 | 落到哪 |
|---|---|---|
| **语料**（K3 长尾资料） | 直接导入 WeKnora，**不经过产品仓库** | WeKnora 知识库 |
| **锚点**（八要素 × 三口吻） | **git PR 进产品仓库** | `content/anchors/*.json` |

- 产的是**语料** → 走下面第二、三、四节。
- 产的是**锚点 JSON** → 直接开 PR 就行，别的都不用。门禁会跑 `loadAnchors` 按
  `src/content/loader.ts` 的 `anchorSchema` 校验，形状不对直接红。**不要在那边手抄一份
  规格当真，PR 门禁才是执行点**；漂移只会表现为 PR 失败，不会表现为线上少讲。

## 二、要你们回答的三个问题（答案决定这批能不能用）

> 2026-11-28 已开给中台：[weknora-data-factory#5](https://github.com/zeemen/weknora-data-factory/issues/5)。
> 下面三问与第三节那五样东西都在那个 issue 里，回答跟进看那边。

### 1. 那台 WeKnora 是什么镜像版本？

**这条最可能让整批白做。** 产品检索必发 `disable_vector_match: true`，而 v0.9.0 有个回归
会把它以 `HTTP 500 Unsupported query shape` 拒掉（[Tencent/WeKnora#4899](https://github.com/Tencent/WeKnora/issues/4899)，
修复 PR #4908 未合并），触发条件正是「问题生成已关闭的文档库」——产品这两个库都是。
所以**语料写得再好，自由问答也引用不到一条**。

- 出路：镜像钉回 `v0.8.3`，或等上游合并。
- 上游 issue 里给的 workaround 是打开问题生成，**我们不用**——那正是下一条在挡的污染。

### 2. 导入时有没有显式带 `"process_config": {"summary_enabled": false}`？

WeKnora 这一项**省略即为 true**。不带，它就会用 LLM 写一段摘要，并把这段摘要
**当成一条可检索的 chunk** 存进库——以「资料」的身份被检索出来喂进 prompt，直接击穿
规格 03 §5.1 的「must_cite 字段不能自由生成」。

而且这一项**不读知识库配置**，没有「在库上关一次」这个选项，只能每次请求带。

核对办法（在库上跑，一句话）：

```sql
SELECT count(*) FROM chunks WHERE chunk_type='summary' AND deleted_at IS NULL;
```

**应当是 0。** 不是 0 就得把那批重导。

> 两条提示：界面上传默认是关的，所以手工传的那批通常没事；走 API 不带就会中。
> 如果你们用的是中台（weknora-data-factory），它的 `deliver()` 发的 body 里
> **这一项还没有**（[#3](https://github.com/zeemen/weknora-data-factory/issues/3) 挂着没修），
> 那就大概率中了。
>
> 这个坑 2026-10-30 在 kb-haoshe 上真踩过：生成的摘要把事实写反了——原文是
> 「夜晚取出**上层**并入下层作床」，它写成「取**下层**木板作为床铺」，而且在
> 「号舍里的木板怎么用」这一问上**排第一**。

### 3. 是按文件上传的，还是走 `/knowledge/manual`？

这决定对账还有没有抓手，以及运营面板看不看得见。

- **按文件**：有 `file_hash`、`title` 是文件名。现有对账（仓库 md5 == `file_hash`）继续成立。
- **走 manual**：那条路**没有文件**，所以 `file_hash` 无从产生、`title` 变成你们给的标题。
  「仓库 md5 == `file_hash`」这条不变式**两端同时消失**——不是不方便，是结构上做不到。
  新抓手只能是**你们的交付记录 ↔ WeKnora 的 `knowledges.id`**，所以请把每篇返回的 id 留下来。
- 连带后果：产品的运营维护面板是**按文件名**对上仓库篇目的
  （`src/http/admin-knowledge.ts` 的 `weknoraIndex`），所以 manual 行在面板上
  既不显示解析状态、也压根不出现——仓库里没有对应文件。

## 三、要交到产品手上的东西

1. **共用实例的地址**（不是你们机器的地址）。
2. **每个场景的知识库 UUID**。场景名取锚点的 `sceneId`，也就是 `content/knowledge/`
   下的目录名；今天只有 `fuzimiao` 和 `nanjing_museum` 两个。
3. **一个 API key，capability 只勾 `retrieve`。**
   产品不需要写权限，**别为了省事给它开 `ingest`**——导入是你们那边的事。
4. **每篇的 `knowledge_id`**（走 manual 的话这是唯一的对账抓手）。
5. **新增场景的话**，给一个**一定在该库语料里出现的专名**，理由见下一节第 3 条。

## 四、产品侧接进来的步骤

1. 配 `WEKNORA_BASE_URL` 与 `WEKNORA_API_KEY`。
2. 配 `WEKNORA_KB_IDS`，格式 `fuzimiao=<uuid>,nanjing_museum=<uuid>`。两个行为要知道：
   半截的项会被直接丢掉（不会变成假库 ID），而**没配到的场景会退化成全库搜**
   （`src/knowledge/weknora.ts` 的 `resolveKbIds`）。全库搜是刻意的——「用户站在哪
   不该决定他能不能问」——但新场景漏配只会悄悄变慢变糊，**不报错**。
3. **新场景要改一处代码**：在 `src/knowledge/readiness.ts` 的 `PROBE_QUERIES` 里补那个专名。
   现在是 `['明远楼', '竹林七贤']`。为什么漏不得：坏掉的 BM25 只在「这个词在这个库里
   真有候选」时才报 500，一个字都不沾时 Postgres 直接短路、回 200 + `data:null`。
   2026-11-08 实测，拿「明远楼」探南博库得到的是一个**看着正常的 empty**，而那个库的
   BM25 同样是坏的（换成「竹林七贤」立刻 500）。**一个探针词等于给每个不含该词的库
   开一张免检通行证。**
4. 跑启动自检，看那条 K3 结论。它的判据刻意不是「后端活着吗」——那天后端活着，
   去掉 `disable_vector_match` 就回 200——而是「**生产实际发的那些请求**都被接受了吗」。
5. **量检索命中，别凭感觉。** 方法在 `knowledge/README.md`：准备探针，每个写明该命中哪篇，
   一半用语料自己的说法、一半用游客的口语，记 hit@1 / hit@3。上一轮 60 个探针，
   补词前 46/60，补词后 55/60，**9 条变好、0 条变差**。
   - 关键词那一行是我们自己写的元数据，不是引文，可以补游客真会用的说法。
   - 但**只补实测打不中的词**，补完再量一遍确认没有退步。给语料集体灌词等于往 BM25
     里掺水，很可能把本来好的那批弄坏。
   - **补词不需要来源背书，补事实才需要。**
6. 跑 `node --run lint:content`。语料里「关联锚点」那一栏：`scene/unknown` 与
   `anchor/placeholder` 是 **error 会挡**；`anchor/not_built` 只是 warn——引了一个还没建的
   锚点不算错。

## 五、有一件事必须在导第一篇之前定下来

今天 **产品仓库是正本，WeKnora 是副本**：`content/knowledge/**/*.md` 说了算，
改内容改仓库、再回传。

数据组一旦成为产出方，这条要反过来，而且**「改仓库再回传」必须同时停掉**。
否则 WeKnora 里有两个写入方，**而且没有任何抓手能发现它们打架**——md5 对账那条
恰好也在同一刻失效（见第二节第 3 问）。

先定边界再导第一篇，比事后分辨哪一版是真的便宜得多。

## 六、顺带一条采集方法论上的保留

南博在线典藏库只放出 11304 件，而官网自述馆藏 43 万件。所以**「库里查不到」只能支持
「无法确认」，不能当否定证据用**。这一条对所有走公开藏品库核验的点位都成立，不止玉衣。
