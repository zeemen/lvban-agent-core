## 1. 全局形状

一个 Node 进程 + 一个微信小程序，中间只有 HTTP 与 SSE。没有消息队列、没有微服务、没有 BFF。

```
┌─────────────────────────────────────────────────────────┐
│ 微信小程序（原生 + TypeScript）                          │
│ 五个页面 · 定位上报 · 相机 · 顺序音频队列 · SSE 分片解析  │
└────────────────┬────────────────────────────────────────┘
                 │ HTTPS / SSE（Bearer 令牌）
┌────────────────▼────────────────────────────────────────┐
│ 旅伴 Agent Core（Fastify，单进程）                       │
│                                                         │
│  接入层    src/http/        路由 · 鉴权钩子 · 错误分类   │
│  编排层    src/agent/       到达 · 问一句 · 游记         │
│  装配层    src/context/state.ts   把 IO 压成一份状态     │
│  决策内核  src/context/ src/planner/   纯函数，无 IO     │
│  适配层    src/models/ src/tts/ src/knowledge/ src/vision/│
│  数据层    src/memory/      唯一写入门 · 仓储 · 瞬时层    │
│  内容层    src/content/ + content/   文件即数据源         │
└──┬──────────┬──────────┬──────────┬─────────────────────┘
   │          │          │          │
┌──▼──┐  ┌────▼───┐  ┌───▼────┐  ┌──▼──────────┐
│ PG16│  │ Redis 7│  │WeKnora │  │ 模型 / TTS  │
│+vec │  │        │  │（检索）│  │（HTTP 外部）│
└─────┘  └────────┘  └────────┘  └─────────────┘
```

进程只有一个入口 [`src/http/server.ts`](../src/http/server.ts)；命令行 [`src/cli/`](../src/cli/main.ts) 复用同一套编排层，不走 HTTP。

## 2. 技术选型与否决记录

记下**否决了什么**，是为了日后有人重提时不必从头吵一遍。

| 位置 | 选了 | 理由 | 否决了 |
|---|---|---|---|
| 服务端 | Node 22+ / TypeScript / Fastify 5 | 与小程序同语言，SSE 与流式控制直接 | — |
| 主存储 | PostgreSQL 16 + pgvector | 记忆是强关系数据（用户→旅程→交互→信号），约束能当第二道防线用；向量将来同库 | 单独的向量库 |
| 瞬时层 | Redis 7 | L0 信号、会话、围栏 tracker、Context 缓存都是「带 TTL 的小状态」 | 放进 PG 再定时清 |
| 长尾检索 | 本地 WeKnora，**只用它的 hybrid-search** | 生成要留在自己这边才管得住受限通道、口吻与字数 | 用它的 chat 接口 |
| 检索召回 | **关掉向量，只留 BM25** | 向量路径永远有答案（拿「量子计算机怎么编程」问夫子庙库也回 5 条）；只有 BM25 会回 0 条，规格 03 §5.3 要的「说不确定」才成立 | 向量 / 混合召回 |
| 模型接入 | 一个 OpenAI 兼容适配器 + 一张供应商档案表 | 三家国内供应商协议一致，差异在模型 ID、思考开关、视觉能力、计价 | 三个适配器；写死模型 ID |
| TTS | **独立的 `TtsAdapter` 契约**，不走 Model Router | 各家协议差异太大，硬塞进 OpenAI 兼容那套会让两边都变形 | 统一成一个 Router |
| 客户端 | 原生小程序 + TypeScript | 核心交互全压在原生能力上（围栏、相机、后台音频、`onChunkReceived`），封装层未必稳定暴露 | Taro / uni-app |
| 流式传输 | SSE（服务端）↔ `enableChunked` + `onChunkReceived`（客户端） | 小程序没有 `EventSource`，这是唯一可行路径（基础库 2.20.2+） | WebSocket |
| 内容载体 | JSON 文件 + 加载期 schema 校验 | 锚点要人工精调、要进 git review、要能被 PR 门禁检查 | 存数据库 |

## 3. 分层边界

### 3.1 决策内核：纯函数，无 IO

这是整套结构里最重要的一条分界。「算不算到达」「此刻该不该开口」「这句话怎么讲」「位置可信到什么程度」全部是不碰 IO 的纯函数：

| 模块 | 回答的问题 |
|---|---|
| [`context/geofence.ts`](../src/context/geofence.ts) | 这次定位算不算到达？不算的话卡在哪一条？ |
| [`context/proactivity.ts`](../src/context/proactivity.ts) | 此刻该不该开口？硬否决是哪一条、打分是哪几项？ |
| [`context/provenance.ts`](../src/context/provenance.ts) | 这个位置是谁说的、可信到什么程度？ |
| [`planner/decide.ts`](../src/planner/decide.ts) | 讲多长、什么口吻、先问还是先答、要不要留钩子？ |
| [`planner/render.ts`](../src/planner/render.ts) | 锚点八要素怎么拼成一段话？ |
| [`planner/register-guard.ts`](../src/planner/register-guard.ts) · [`cite-guard.ts`](../src/planner/cite-guard.ts) | 这段话口吻退化了吗、有没有念出没依据的事实？ |
| [`planner/soft-hint.ts`](../src/planner/soft-hint.ts) | 不开口那一档给什么？（气泡上写哪句、点一下播哪个音频） |
| [`planner/sentence.ts`](../src/planner/sentence.ts) | 流里的字怎么增量切成可送 TTS 的句子？ |

这样划的三个理由，按重要性排：

1. **现场最常被问的是「为什么这里没说话」。** 纯函数才能带着 `reason` / `blockedBy` / `vetoedBy` 原样返回，并在运营后台回放。
2. **可单测、可回放。** 决策层的用例不需要数据库（见第 10 节 CI 的「零依赖」那一层）。
3. **换模型不动策略。** 决策先出，文案后生成；模型是适配层的事。

反面约束同样成立：决策内核里**不允许**出现 `pool.query` 或 `fetch`。一旦需要数据，就该由装配层查好了传进来。

### 3.2 装配层：唯一把 IO 和决策缝起来的地方

[`context/state.ts`](../src/context/state.ts) 的 `buildContextState` 是全链路唯一的汇聚点：四条聚合 SQL（此处被问过几次、有没有说累、停留多久、近 20 分钟与前 20 分钟的交互数对比、这趟访问过哪些锚点）+ 记忆钩子 + L0 的 `lastSpoke` / 连续忽略数 → 派生 interest / fatigue / activity → zod 校验 → 缓存 30 秒。

它的输出 `ContextState`（[`domain/context-state.ts`](../src/domain/context-state.ts)）是决策内核唯一的输入形状。规格 03 的「商户不进讲解」这条红线就落在这个形状上：`PlanInput` 里**结构上没有商户字段**，不是靠调用方不传。

### 3.3 适配层：每个外部能力都要能回答「我现在可用吗」

不是「调用时抛错」，而是在用户动作之前就能判定：

| 能力 | 判定函数 | 不可用时 |
|---|---|---|
| 模型·视觉 | `visionAvailability()` [`models/router.ts:148`](../src/models/router.ts:148) | 「拍一下」退回 `fallback_ask`，不在快门按下后才报错 |
| TTS | `ttsAvailability()` [`tts/availability.ts`](../src/tts/availability.ts) | 整条应答降级为只显示文字，不发 `audio` 事件 |
| 微信登录 | `requireWxConfig()` [`auth/policy.ts`](../src/auth/policy.ts) | 503 并说清缺哪个变量，而不是拿空密钥去打微信换一个难归因的 errcode |
| 长尾检索 | 无需判定：`retrievePassages` 永不抛 | 这次不带长尾证据，回答照常 |

**价格与能力不靠猜。** 视觉能力按模型 ID 判定（同一个 DeepSeek 账号，`deepseek-flash` 吃图、`deepseek-v4-pro` 不吃），价格未经官方页面核实就不写入档案——没有 pricing 的档案只统计 token、`costCny` 返回 `null` 并计入 `unpricedCalls`。宁可没有数字，不要有错的数字。

### 3.4 数据层：一个门，两道防线

所有记忆写入只能经过 [`memory/gateway.ts`](../src/memory/gateway.ts) 的 `writeMemory`，业务代码不允许直接 INSERT。四条红线里三条在这里执行，第四条在类型层：

| 红线 | 第一道（网关） | 第二道（数据库） |
|---|---|---|
| 系统推断不进长期记忆 | `source === 'system_inferred'` 分流进 L0（Redis，TTL 24h） | `preference.source` 的 CHECK 只含 `explicit` / `user_confirmed` |
| 没有 open 的 Journey 就没有采集 | journey 状态必须是 ACTIVE / IDLE | 外键 + `journey.state` 的 CHECK 枚举 |
| 室内不伪造精确位置 | [`context/attention.ts`](../src/context/attention.ts) 落位前校验 id 指得到锚点、场景与旅程一致 | `location_event.source` 枚举 + `CHECK (source <> 'vision_anchor' OR confidence IS NOT NULL)` |
| 商户不进讲解 | — | — （在 `PlanInput` 的类型里，结构上不存在） |

「绕过网关直接写库也会被数据库约束拦住」这件事有集成用例看着（`tests/integration/gateway.test.ts`）。

**但读的那一侧没有门，这是目前最薄的一处。** 2026-11-03 加静默卡片时踩到了：
卡片为了留痕写进 `interaction`（`role='agent'`、带 `anchor_id`），于是四个
「这句话说给用户听过没有」的读取方同时改变了含义——跨旅程的「已听过」、
游记的到访锚点、疲劳推断的交互密度窗口、语义足迹的主题聚合。写入侧一个字都没错，
`channel` 枚举早就有 `silent_card`，数据库约束照样放行，而后果是一次气泡
把 Top 30 锚点永久标成「已听过」、此后只剩气泡，自我强化且不报错。
现在四处都带上了 [`repo.notSilentCard()`](../src/memory/repo.ts)，但那只是四处字符串约定——
**往 `channel` 里再加一个值，编译器仍然拦不住**。真正的修法是把 `interaction`
的读取也收进带类型的仓储函数，让新 channel 迫使每个读取方重新表态（见第 11 节）。

## 4. 三条运行时路径

### 4.1 室外：进围栏 ≠ 开口

```
客户端批量上报定位
  → 精度过滤（> 50m 丢弃）              ingest.ts
  → pickActiveFence：同一时刻只有一个 active poi
  → evaluateGeofence：六条件 + 进出迟滞（出圈多走 15m）
                      触发时把那条定位的精度记进 tracker
  → arrive 事件 → writeMemory(location_event, source=geofence)
       ↓  （到此只是「到了」）
POST /v1/journeys/:id/arrive
  → buildContextState
  → decideProactivity：八条硬否决 → 打分 → 模式阈值 → 三值
                       → 封顶：频次到了 / 精度 25–50m，SPEAK 降成 SOFT_HINT
  → SPEAK      decidePlan + renderFromAnchor（零模型调用）
                 → 口吻守卫 → 写 interaction + 记 lastSpoke / lastProactive
  → SOFT_HINT  buildSilentCard（气泡，不出声，文案同样取自锚点）
                 已听过 → 换反问/观察，不重播开场钩子（规格 03 §3.3）
                 → 写 interaction(channel=silent_card)，不记 lastSpoke
                 这条行不算「讲过」：四个读取方都排除它（§3.4）
  → SILENT     什么都不发，但带着 reason 回去
```

**频次到了是降一档，不是沉默。** §7.4 的「最大主动频次」（同游 8 分钟 /
亲子 6 分钟 / 轻导览 15 分钟）不在 §7.2 的硬否决表里，所以它不否决，
只把 SPEAK 压成 SOFT_HINT。它数的也只是**主动开口**：回答用户提问不算，
出气泡不算（没出声）。§7.3 第 7 行的频次扣分（「已开口次数 > 时长/10min」）
数的是同一件事，所以 `l0:pcount` 和 `l0:proactive` 由同一个函数一起写——
口径分家就会变成两条互相打架的频次控制。这就是 L0 里 `l0:spoke` 与 `l0:proactive` 两个键
各管一件事的原因——前者管「别叠话」（60 秒），后者管「别太密」。

**精度不够也是降一档，不是沉默。** 规格 02 §2.2 给的是三档不是两档：> 50m 丢弃、
25–50m 降权（「只能触发软提示，不能触发自动讲解」）、≤ 25m 可信。中间那一档
2026-11-07 之前整条不产生事件——围栏层拿 25m 当丢弃线，于是「只能软提示」
在代码里等于「什么都不触发」，而夫子庙是密集街巷 + 水体 + 夜间，25–50m 是常态。

这一档的判定**只在决策内核一处**（`isAccuracyDegraded`）：围栏层只管丢弃线，
再把触发那一刻的精度记进 tracker 的 `lastTriggeredAccuracyM`。两处各判一次
迟早漂成两套阈值。精度必须从服务端读回来而不是让 `/arrive` 再报一遍——
那是客户端另起的一次调用，不报就等于这一档的降权不生效。装配层取
客户端自报与服务端记录里**更差**的那个：可以补充，不能用一个更好的数洗掉降权。

降权也不把置信度拖下去：§7.2 的 0.6 否决线问的是「知不知道人在哪」，
25–50m 是「大概知道」，不是「不知道」——压到线下就变成整条沉默，
而规格要的恰恰是这一档还能出气泡。

两段判断被刻意分在两个文件里：产生事件和决定开口是两件事，混在一起就再也说不清「为什么这里没说话」。

### 4.2 室内：不问「人在哪」，只问「在看哪件」

室内根本不做空间定位——绝大多数博物馆支持不了，手机 GPS 也到不了展厅级。于是 `locationSource` 在室内只有三种合法取值：游客点选（1.0）、拍照识别（VLM 的 top-1 分）、`inferred`（≤ 0.6，含义就是**我们不知道**）。客户端在室内声明 `geofence` 一律不认，连它报的分数也不信。

`inferred` 压在 0.6 以下不是随手取的：主动性引擎拿 0.6 当硬否决线，给室内默认 0.9 等于让这条线永远失效。

拍照链路的三个结构性决定：

- **候选集先按服务端自己知道的 `journey.scene_id` 收窄**，再让客户端的 `zoneHint` 在场景内缩小。场景不能交给客户端决定，否则在南博拍一张可能认出夫子庙的点位。
- **只有 `auto_accept` 才落位**，事件 kind 用 `confirm_zone` 而非 `arrive`（室内没有「到达」这种事件），并把 `locationEventId` 交回客户端供撤回。
- **回执的三步顺序是刻意的**：先落位 → 再撤回 → 最后记命中率。点选的 id 指不到东西时整条请求 400，而此前什么都没动过；反过来先撤后落，一旦落位被拒，游客就既丢了原来那条又没拿到新的。

落位之后下一句不必重报来源：装配层在室内会自己从本旅程已落位的注意力里读（TTL 5 分钟，过了就当不知道）。

### 4.3 问一句：主链路

事件顺序就是用户的体感（[`agent/respond-stream.ts`](../src/agent/respond-stream.ts)）：

```
t=0      垫音事件（文字 + audioKey，客户端播本地预合成音频）
         ↑ 必须在任何网络调用之前发出
t≈23ms   K3 检索（BM25，800ms 超时，失败就空着）—— 藏在垫音后面
t≈1.0s   模型首个正文 delta（思维链事件丢掉，不给用户）
t≈1.4s   第一句凑齐 → sentence 事件 → 立刻送 TTS → audio 事件
...      后续句子在用户听前一句时合成，都不在关键路径上
末尾     口吻守卫 + 回查（只记不拦）→ 写 interaction（带 chunk 溯源）
         → done 事件带全套 timing
```

`audio` 事件**只带 audioKey，不内联字节**：base64 塞进 SSE 会让事件流变重，而且没法交给 CDN。客户端去 `GET /v1/audio/<key>` 取，那条路由对 key 做路径穿越校验（key 来自客户端），并带 `immutable` 长缓存头。

**流式这条路付的代价要说清**：第一个字送出去就收不回来，所以守卫只能作遥测。预防全靠 system prompt——两条路径**共用同一份** [`agent/prompt.ts`](../src/agent/prompt.ts)，各写一份的话质量约束迟早漂移。需要强校验的行后生成（游记）继续走非流式的 `onQuestion`，那条路径保留「命中即重写一次」，回查二次仍不过就整句降级成「这个我手头的资料对不上，不敢跟你瞎说」。

## 5. 数据架构

### 5.1 三层记忆

| 层 | 存哪 | 生命周期 | 谁能写 |
|---|---|---|---|
| L0 瞬时 | Redis，TTL 24h | 随旅程结束 + 24 小时消失，**永不落库、永不参与蒸馏** | 系统推断（`system_inferred`） |
| L1 本次旅程 | PG：`interaction` / `location_event` / `journey_signal` / `raw_track_point` | 随旅程；原始轨迹 7 天销毁 | 网关 |
| L2/L3 长期 | PG：`preference` / `identity_trait` | 跨旅程，带强度与衰减 | 只能由行后蒸馏或用户亲口确认升上来 |

从 L0 升到 L2 只有一条正门：用户在行后回顾页点确认，以 `user_confirmed` 写入。

### 5.2 行后蒸馏

[`memory/distill.ts`](../src/memory/distill.ts)，以 `journey.distilled_at` 幂等、可重放：

- **D2** 信号 → 偏好：同类信号够数（阈值 2）或用户确认
- **D3** 偏好 → 身份：跨 ≥ 3 次旅程且 party 无关
- **D4** 轨迹 → 语义足迹：生成足迹，原始点标记 7 天销毁
- 强度公式与衰减半衰期（180 天）全部外置在 [`config/index.ts`](../src/config/index.ts) 的 `distillation`，等真实数据校准

### 5.3 内容：文件即数据源

锚点、围栏、垫音都是 git 里的 JSON 文件，在加载期用 zod 校验（[`content/loader.ts`](../src/content/loader.ts)）。

**加载失败就整体失败，不降级跳过那一个锚点。** `approved` 这个状态是史实能否进入游记的唯一开关，schema 要求：`YYYY-MM-DD` 审校日期、待核清单清空、以及**双签两方各一个中台账号**（`content_owner` + `history_advisor`，不能同一账号兼任）。不满足就让整个内容加载抛错——「静默地少讲」是这个项目认定的最坏结果，契约违反要响，不要悄悄过。

## 6. 四种契约，四个失败时点

跨边界的约定如果只靠文档，漂移了只会表现成「有时候没声音」。所以每一种都钉在一个会响的时点上：

| 契约 | 谁和谁之间 | 失败时点 |
|---|---|---|
| SSE 事件 | 服务端 ↔ 小程序 | **编译期**。[`miniprogram/shared/stream-events.ts`](../miniprogram/shared/stream-events.ts) 是共用契约，服务端一条 `[StreamedEvent] extends [WireEvent]` 断言保证不漂（元组包裹是必要的：裸的联合会逐成员分发，断言会形同虚设） |
| 锚点八要素 | 内容 ↔ 代码 | **加载期**。schema 不过就起不来 |
| 模型适配器 | 代码 ↔ 供应商 | **测试期**。`tests/integration/adapter-contract.test.ts` 同一套断言跑 mock 和真实供应商（没配 `PROBE_PROVIDER` 自动跳过真实那组） |
| 语料与锚点交付 | 知识库供应链中台 ↔ 本仓库 | **PR 门禁**。契约见 [`content/supply-chain-contract.md`](../content/supply-chain-contract.md)；执行点是内容门禁工作流。中台是 Python，导不进这边的 zod schema，所以 PR 是唯一的强制点——漂移表现为一个失败的 PR，而不是线上一个静默的缺口 |

## 7. 可用性与降级矩阵

这个产品的一贯姿态：**可降级的子系统坏掉，不许拖垮主链路；不可降级的约束违反，必须响。**

| 依赖 | 坏掉时的产品表现 | 实现位置 |
|---|---|---|
| 模型 | 流式发 `error` 事件带一句能说出口的 `fallbackText`；非流式由 `classifyError` 归类 | [`respond-stream.ts:252`](../src/agent/respond-stream.ts:252) |
| WeKnora | 少一条引用，回答照常。语音优先的产品里，一条引用换不来一次卡顿。**但「被拒」和「查不到」要分开记**——两者在产品里都是「模型说不确定」，混在一起这条链路可以整月是死的（2026-11-08 实测过一次） | [`knowledge/weknora.ts:208`](../src/knowledge/weknora.ts:208)、[`knowledge/readiness.ts`](../src/knowledge/readiness.ts) |
| TTS | 只显示文字，不发 `audio` 事件，不报错 | [`tts/availability.ts`](../src/tts/availability.ts) |
| VLM | 「拍一下」退回「问一句」，与命中率熔断同一条降级路径 | [`models/router.ts:148`](../src/models/router.ts:148) |
| 定位精度不够 | 丢点 / 不触发——**闭嘴而不是猜** | [`ingest.ts:48`](../src/context/ingest.ts:48)、[`geofence.ts:90`](../src/context/geofence.ts:90) |
| 预合成音频缺失 | 取音频回 404（不临时合成）；启动时核对并分级报告：缺文件 warn、音色对不上 error | [`server.ts:35`](../src/http/server.ts:35)、[`tts/readiness.ts`](../src/tts/readiness.ts) |
| K3 取不到证据 | 自由问答只剩锚点与记忆两级，模型按证据纪律说不确定；**启动时按 error 报出来**，不再静静退化 | [`server.ts:58`](../src/http/server.ts:58)、[`knowledge/readiness.ts`](../src/knowledge/readiness.ts) |
| 回查拿不出依据 | 非流式整句降级并把人引向现场说明牌；流式只能记录 | [`respond.ts:333`](../src/agent/respond.ts:333) |
| **PostgreSQL** | **硬依赖，无降级** | `/health` 跟着红 |
| **Redis** | **硬依赖，无降级**：会话、L0、围栏 tracker、Context 缓存都在它上面 | `/health` 跟着红 |

启动时的音频核对放在 `listen` **之后**且自己兜住异常，是同一条原则的应用：为一个可降级的子系统拒绝启动，炸的范围比问题本身大；但漏跑一次预合成的线上表现是「该出声的地方没出声」而日志里一个字都没有，所以必须报。

`/health` 真打一次 PG 和 Redis（各 2 秒超时），不只看进程活着——容器停了而进程还在，是联调时最容易看岔的一种故障。

## 8. 安全与合规架构

- **身份只认令牌。** 32 字节随机令牌，Redis 里存 SHA-256 而非令牌本身，30 天滑动续期。请求体里的 `userId` 只在匿名联调时作数（[`http/auth.ts`](../src/http/auth.ts) 的 `requireSelf`）。否则填别人的 UUID 就能读到别人的记忆——对一个主打青少年记忆的产品这是红线。
- **解析与要求分两步。** 钩子对所有请求解析一次身份，强不强制由每条路由自己决定：PRD U01 允许未授权浏览，只是不能开旅程，不能一刀切全局 401。带了无效令牌一律 401，和「压根没带」区分开。
- **归属校验下沉到旅程。** 拿到 `journeyId` 也驱动不了别人的行程；旅程不存在时不在鉴权层报，避免泄漏存在性。
- **登录只取 openid。** 不索取手机号，`session_key` 拿到即丢弃——不解密任何加密数据就不需要持有它，少存一个凭证少一处泄漏面。
- **Journey 是采集的最小授权单元。** 不做全天候或后台持续追踪；`consent_snapshot` 在开旅程时连时间戳一起落库。
- **原始轨迹二次校验。** `track_consent` 不是 `full_track` 的，网关直接丢弃——服务端不信任客户端已经问过。
- **未成年人。** 14 岁以下须监护人授权在位，缺了网关拒写。
- **后门与强制鉴权不并存。** `/v1/dev/users` 是无需凭证凭空造身份的后门，`AUTH_REQUIRED` 开启后它返回 404；该开关不设时跟着 `WX_APPSECRET` 走。
- **运营后台默认关闭。** 没有 `ADMIN_TOOLS=true` 就一条路由都不注册：它能按任意地址发请求、能读仓库内容，不该跟着业务服务一起上线。它也刻意**不做写回 WeKnora**——那要 ingest 提权，应该由人在知道自己在干什么的时候点，不该藏在一个默认开着的页面后面。
- **路径穿越。** `/v1/audio/*` 的 key 来自客户端，解析后必须仍在缓存目录内。
- **密钥一律走环境变量**，`config/index.ts` 的 `required()` 在缺失时直接抛错并指向 `.env.example`。

## 9. 性能与成本架构

### 9.1 延迟：三层叠加

最初实测首个正文 delta 要 3718ms（最差 10.7s），而 qa 任务的预算是 1200ms。拆开测之后的结论是**流式本身不是答案**——推理模型先流几百字思维链再流正文，开着思考做流式，用户仍要等 3.4–6.6 秒。

| 手段 | 作用 | 实测 |
|---|---|---|
| 按任务关深度思考 | 对话类不需要思维链 | 3718ms → 1017ms |
| 流式 + 增量分句 | 第一句凑齐就送 TTS | 第一句 1412ms（整段 2023ms） |
| 预置垫音 | 本地预合成音频盖住剩下那一秒 | 用户听到声音 **6–7ms** |

策略按任务分：`intent` / `qa` / `copy` 关思考，`planner` 保留（深度解释规划要强推理，且不在用户等待的关键路径上）。预算表在 [`models/types.ts:14`](../src/models/types.ts:14)：intent 150ms / qa 1200ms / planner 800ms / vision 1500ms / travelogue 15s（长文且不在交互路径上）。

### 9.2 缓存三类

| 类型 | 寻址方式 | 为什么 |
|---|---|---|
| 固定台词（垫音、Top 30 锚点开场段） | 作者指定的稳定路径 | 每个用户听到的都一样：一次合成永久复用，现场零延迟零成本 |
| 动态句子 | 内容哈希（文本 + 音色 + 语速 + 编码） | 改了音色自然产生新 key |
| Context State | 旅程维度，TTL 30s | 一次交互里反复用 |

固定台词的路径里**不含供应商和音色**，所以单看「文件在不在」会掉进一个静默的坑：用 mock 预合成过一轮再换真供应商，presynth 会全部跳过、线上播的是假音频且不报错。`audio-cache/manifest.json` 记下每条音频是用谁、什么音色、什么语速、什么文案合成的，任何一项对不上就重合成并说明原因。

### 9.3 成本账本

[`models/router.ts`](../src/models/router.ts) 的 ledger 按任务记调用数、token 数、**思维链 token 单独记账**（它用户看不见但要计费）、超预算的调用，以及 `unpricedCalls`。`/health` 顺带把账本吐出来。

锚点命中的讲解**零模型调用**（走人工精调的八要素），只有自由提问才走 Model Router——成本与首句延迟同时受控。

## 10. 可观测性与质量门

### 10.1 每个决策都要能自证

| 字段 | 回答 | 来源 |
|---|---|---|
| `blockedBy` | 这次定位为什么没触发到达 | 围栏 |
| `vetoedBy` / `reason` | 为什么没开口 / 打分是哪几项 | 主动性引擎 |
| `plan.reason` | 为什么这么讲 | Planner |
| `timing` | 垫音、首 delta、首句、首音各在第几毫秒 | 流式应答 |
| `evidenceRefs.k3` | 这句话当时看过哪几个 chunk | 写入网关 |
| `memory/:id/why` | 为什么记住了这条 | 记忆检索（证据随结果一起返回，不另查一次） |
| `memory_audit` | 谁在什么时候写了/拒了/删了什么 | 网关 |

### 10.2 两个工作流，刻意分开

| 工作流 | 跑什么 | 性质 |
|---|---|---|
| [`content-gate.yml`](../.github/workflows/content-gate.yml) | typecheck + `lint:content` + 门禁自己的用例 | **约 1 秒、零依赖**：不要 PG / Redis / WeKnora / 密钥。内容 PR 不该为了等集成环境排队 |
| [`full-suite.yml`](../.github/workflows/full-suite.yml) | 服务容器 + 迁移 + presynth + 全量用例 + 覆盖率阈值 | 跑门禁拦不住的那一类 |

内容门禁的「零依赖」是一条需要被守护的性质，不是自然成立的：2026-10-31 之前 `lint:content` 为了收尾方便 import 了 `db/pool`，连带 import `config`，而 `config` 缺 `DATABASE_URL` 时直接抛错——本机有 `.env`，谁都看不见。现在有一条用例起子进程、抹掉 `DATABASE_URL` 跑一遍，专门看着这件事。

门禁的分级也是刻意的：**错误必须修复后方可合并，警告不拦**（待双签、关联锚点还没建，那是内容负责人的待办清单，不是交付缺陷，拦了只会逼人造假）。

覆盖率阈值（lines 80 / functions 80 / branches 75 / statements 80）写在 `vitest.config.ts`，`full-suite` 用 `coverage` 而不是 `test` 就是为了卡住它。测试进程把 `MODEL_PROVIDER` / `TTS_PROVIDER` 钉成 mock，所以常规测试不会去打收费接口，也不会因为谁改了 `.env` 而行为不同。

## 11. 已知架构缺口

按「会不会悄悄出错」排序，不按工作量排。

1. **家长端静默提示没有实现。** 规格 03 §8.3 要的是另一回事：`foreground_user = "parent"` 的管家口吻卡片（节奏 / 休息 / 洗手间 / 进度 / 消费，≤ 1 次 / 20 分钟）。`familyContextSchema` 已经在 [`context-state.ts`](../src/domain/context-state.ts) 里（含 `foregroundUser`），但装配层从不填充它，所以这条管线没有输入。注意它和 §7.1 的 SOFT_HINT 只是共用 `silent_card` 这个 channel，不是同一个功能。
2. **`interaction` 的读取方靠四处字符串约定，不是类型。** 上面 §3.4 那段说的就是它：新增一个 `channel` 会静默改变每个「讲过没有」判断的含义。眼下四处都对了，但下一次仍然只能靠人记得。
3. **§7.5 的「被忽略」判定整条没有实现。** `bumpIgnored` / `resetIgnored` / `markIgnored` 零调用方，只有 `readIgnored` 被读；所以 `consecutiveIgnored` 永远是 0，§7.2 那条 `consecutive_ignored ≥ 2` 的硬否决永远不会触发，规格要求的「需要我安静一会儿吗」显式开关也不存在。静默卡片这一档更是完全没有忽略计账——一张没人点开的气泡和一次被忽略的讲解，现在都不留痕。
4. **静默卡片没有自己的频次预算，这是刻意的，但需要现场验。** §7.4 的间隔只压「开口」，气泡不受限，理由是再压一次这一档就等于不存在；现在唯一的刹车是每个围栏自己的 30 分钟冷却与进出迟滞。而 §7.1 把这一档写作「气泡/**震动**」——震动是会打扰人的，夫子庙 500m 内有 12 个点位，一个被频次压着的用户理论上可以在每个点位各收一次震动。先这样，路测时专门看这一条。
5. **`decision.nextAction` 没有消费方。** Planner 算得出「下一站」，但没有任何地方读它，所以到不了用户。`lint:content` 的 `next_action/dangling` 只报警告就是这个缘故。
6. **围栏坐标是占位值**（`calibrated: false`），必须按规格 02 §9.3 现场实测后替换。室外链路目前只能在开发者工具里按按钮模拟，但走的仍是服务端真实的六条件判定。
7. **锚点内容只有 8 个且全是 `draft`**（M1 门槛 30 个），所以游记里不会出现任何史实——这是规格 04 §7.1 的硬约束生效，不是 bug。夫子庙「企划书点名」的 6 处已建完，南博还只有 2 件；`njm_yuyi` 刻意没建：2026-11-09 查证确认大云山一号墓、二号墓各出土一套**金缕**玉衣（江苏省文旅厅官网刊载南博考古研究所发掘简介），但**南博名下另有一件东汉银缕玉衣**（徐州土山一号汉墓），企划书写的「金缕玉衣」指哪一件无来源可定；且规格 04 §4.3 要的「常设展陈、不选临展」没有任何官方来源支持——南博官网典藏库搜「玉衣」0 件，提到玉衣的展览全是临展或外展，历史馆 3 展厅常设展页全文无「玉衣」二字。完整证据链见 README；对中台的字段要求见 [weknora-data-factory#4](https://github.com/zeemen/weknora-data-factory/issues/4)。
8. **没有 embedding。** 记忆检索的向量相似度目前用主题重叠度代替（`topicSimilarity`，接入后替换该函数即可）；K3 的向量召回是**刻意**关掉的，两件事不要混。
9. **K3 长尾检索当前取不到证据，而原因在上游。** `disable_vector_match: true` 被 WeKnora v0.9.0 以 `HTTP 500 Unsupported query shape` 拒掉（[Tencent/WeKnora#4899](https://github.com/Tencent/WeKnora/issues/4899)，修复 PR #4908 未合并），触发条件正是「问题生成已关闭的文档库」。两条诱人的绕法都不能走：打开问题生成会往库里写模型生成且可检索的问答（[weknora-data-factory#3](https://github.com/zeemen/weknora-data-factory/issues/3) 挡的就是这个），改成混合检索则只是让 `retainPartialResults` 吞掉失败的关键词召回、悄悄退回「永远有答案」那一档——而关掉向量的全部理由就是不要它。出路只有钉回镜像 `v0.8.3` 或等上游。**这一条值得记住的不是故障本身，而是它为什么能活那么久**：`retrievePassages` 的降级是刻意的（语音优先），于是故障的表现和「库里确实没有」完全一致；而所有 WeKnora 用例都 mock 了 `fetch`，没有一条用真实请求体打过真实后端，所以 863 条用例全绿。2026-11-08 补了启动自检（[`src/knowledge/readiness.ts`](../src/knowledge/readiness.ts)）并把「被拒」和「查不到」在日志里分开。

10. **室内的「已访问点位推断」不做。** 规格 02 §4.1 ④ 那套展厅序列模型没有实现，而且按「室内不伪造精确位置」这条也不该去实现。看到 `inferred` 不要想着补个推断把它填上。
11. **真机未验。** `onChunkReceived` 的真机表现、后台音频、定位权限弹窗、相机与相册授权、微信登录真实 appsecret、TTS 真实音色都还没跑过。「拍一下」的客户端链路（`utils/photo.ts` + `shared/vision-flow.ts` + 行中页）2026-11-10 已接通并有用例，但 `wx.chooseMedia` / `wx.compressImage` 的真机行为——尤其压缩后还超 300KB 的概率——只有真机测得出来。
12. **图片没有直传对象存储。** 规格 02 §4.2 写的是「上传（HTTPS，直传对象存储，回传 key）」，现在是把压好的图做成 data URI 直接当 `imageKey` 发给自己的服务端。代价有两条：base64 比原字节多约三分之一，请求体也就大三分之一；图片经过我们自己的服务，不是客户端直传。换直传时接口不用动（`imageKey` 换成对象存储回传的 key，[`src/models/image-url.ts`](../src/models/image-url.ts) 三种形式都认）。

数据库端口有意避开默认值（PG `55432`、Redis `56379`），避免与本机已有实例冲突。
